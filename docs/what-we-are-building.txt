Selected track:

Track C — SentinelAPI: Zero-Trust API Vulnerability Scanner

Goal:
Build a security scanner that can ingest an OpenAPI/Swagger specification or observe/test a sandboxed API, automatically detect API vulnerabilities, explain the findings, and generate reproducible PoCs.

Target users:
- Backend engineers
- Platform engineers
- AppSec/security teams

Important problem areas from the problem statement:

- Authentication misconfiguration

# PRIMARY VULNERABILITY — BOLA / IDOR

BOLA = Broken Object Level Authorization.

The vulnerability happens when a user is authenticated but can access another user's resource simply by changing an object ID.

Example:

User A:

GET /users/101/orders
Authorization: Bearer USER_A

→ 200 OK

Then:

GET /users/102/orders
Authorization: Bearer USER_A

If user 102 belongs to another user and the API returns:

→ 200 OK

then BOLA exists.

The server authenticated User A correctly, but failed to verify whether User A is authorized to access resource 102.

SentinelAPI should detect this automatically.

Expected flow:

User A
  ↓
GET /users/101/orders → 200 OK
  ↓
change ID
  ↓
GET /users/102/orders → 200 OK
  ↓
BOLA DETECTED

Finding should contain:

[HIGH] BOLA / IDOR

Endpoint:
GET /users/{userId}/orders

Authenticated User:
User A

Original ID:
101

Modified ID:
102

Expected:
403 Forbidden

Actual:
200 OK

Impact:
User A can access another user's resource.

Then generate a reproducible PoC:

curl -X GET \
  http://localhost:8000/users/102/orders \
  -H "Authorization: Bearer <token>"

# SECOND VULNERABILITY — EXCESSIVE DATA EXPOSURE

Example:

GET /api/users/101

Expected response:

{
  "id": 101,
  "name": "Yuvraj"
}

But vulnerable API returns unnecessary/sensitive fields:

{
  "id": 101,
  "name": "Yuvraj",
  "email": "...",
  "phone": "...",
  "password_hash": "...",
  "internal_role": "admin",
  "reset_token": "..."
}

SentinelAPI should inspect API responses and identify potentially sensitive/unnecessary fields.

This scanner should eventually have configurable sensitive-field detection rather than blindly declaring every large response vulnerable.

# OPENAPI

The sandbox API should expose an OpenAPI specification.

SentinelAPI should ingest the sandbox's OpenAPI JSON/YAML.

End-to-end flow:

Vulnerable FastAPI
       ↓
OpenAPI specification
       ↓
SentinelAPI
       ↓
Parse endpoints
       ↓
Select vulnerability
       ↓
Run tests
       ↓
Collect evidence
       ↓
Severity engine
       ↓
PoC generator
       ↓
Terminal report

This is important because we want the scanner to actually consume the API's specification rather than relying on hardcoded endpoints.
